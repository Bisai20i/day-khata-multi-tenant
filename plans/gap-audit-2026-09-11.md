# Gap and correctness audit, 2026-09-11

Scope: legacy `day_khata` compared against `day-khata-multi-tenant` at `development` `038a271` (clean tree).
Method: 7 parallel read-only agents (sales parity, purchase/inventory parity, accounting/reports parity,
backend money precision, frontend calculation parity, sales billing-record integrity, purchase/ledger
integrity), then coordinator re-verification of every P0 against the code. Nothing was modified; no tests,
builds, migrations or database commands were run.

Markers: **[V]** = re-verified by the coordinator (code read, or pure-arithmetic `php -r` on this machine's
PHP 8.4.14). **(n)** = found independently by n agents.

---

## 0. Headline

- Parity is good: 64 legacy capabilities verified equivalent or better across sales, purchase/inventory and
  accounting. The feature gaps that remain are mostly compliance and reporting, not whole modules.
- It is **not yet safe to bill real customers**. 20 P0 issues cluster into four root causes:
  1. Money math is PHP/JS float + `round()` everywhere. PHP 8.4 changed `round()` so ordinary
     `qty * rate` lines now mis-round by one paisa about 0.4% of the time.
  2. A voucher's date is never checked against the fiscal year it posts into.
  3. Inventory is not in the books: no closing stock in P&L, Balance Sheet or year-end close, and the
     stock unit cost recorded on purchases is wrong for alternate units.
  4. Document lifecycle: unlocked status transitions, cancel reversals burning invoice numbers, returns
     ignoring unit conversion, pending/rejected returns counted as real.
- Two frontend defects block daily use right now: Save & Print throws (and POS keeps the posted cart), and
  `Input.vue` drops `step`, so the browser refuses any decimal entry on submit.

Environment facts: PHP 8.4.14 locally and in CI, `composer.json` still allows `^8.3`. `bcmath` and `intl`
loaded. `brick/math 0.18.0` is already installed (Laravel dependency). Tests run on SQLite, which cannot
reproduce MySQL per-column DECIMAL rounding or `lockForUpdate`; production is MySQL strict mode.

## 1. P0: fix before any tenant bills real customers

### 1A. Money precision

**P0-1 Line amounts, discounts and depreciation mis-round on PHP 8.4 [V]**
- `app/Models/Sale.php:239,241,300`, `Purchase.php:226,228,253`, `StockAdjustment.php:171`,
  `StockTransfer.php:134`, `StockConversion.php:155`, `FixedAsset.php:205-206`, `QuotationController.php:140`.
- Proof: `round(1.5*0.15, 2)` = 0.22 (should be 0.23). 28.5 x 14,209.99 = 404,984.71 (should be .72).
  15% of 4.10 = 0.61 (should be 0.62). 15% depreciation on 43,14,071.10 is one paisa low.
  Measured: 0.39% of 2dp x 2dp products wrong. 13% VAT on a 2dp base happens to be safe (ties land on
  exactly representable N.50), everything else is not.
- Fix: brick/math `BigDecimal` value objects, HALF_UP, see section 6.

**P0-2 Journal balance check passes, MySQL stores an unbalanced voucher [V]**
- `app/Models/JournalVoucher.php:147-171` sums raw floats and compares `round(sum,2)`; `:139` `createMany`
  stores raw values and MySQL rounds each line separately.
- Proof: Dr 333.333 x 3 against Cr 999.999 passes, stored as Dr 999.99 / Cr 1000.00. Reachable from the
  JV form (`JournalVoucherController.php:48-49`) and the opening-balance CSV import
  (`AccountController.php:205-233`). Year-end close then fails or skips the opening voucher
  (`FiscalYear.php:323`).
- Fix: round every line to 2dp before validating, store exactly that, compare exactly.

**P0-3 Partial returns re-derive amounts by division and lose paisa [V]**
- `SalesReturn.php:519-525` (`line_total / quantity * returnQty`), `PurchaseReturn.php:179-186`, TDS share
  (`SalesReturn.php:167,359`, `PurchaseReturn.php:233`), discount ratio (`SalesReturn.php:485-489,523`).
- Proof: line qty 3 totalling 100.00 returned 1+1+1 credits 99.99 (200.00 credits 200.01).
  The residue is then hidden by `<= 0.01` filters in `ReceiptController.php:40`, `PaymentController.php:40`,
  `SalesPurchaseReportController.php:287,334`, `TdsReportController.php:94,120`.
- Fix: the return that consumes the last remaining quantity gets "original minus everything already
  returned"; others use `line_total * qty / line_qty` with a single rounding. Same rule for VAT, discount
  and TDS shares.

**P0-4 0.01 tolerances accept one-paisa errors (2)**
- Partial settlement `abs((cash+bank) - due) > 0.01`: `Sale.php:333`, `Purchase.php:361`,
  `CapitalSale.php:176`, `CapitalPurchase.php:183`. Accepted mismatch leaves +-0.01 on the party.
- Allocation `allocation > outstanding + 0.01`: `Receipt.php:141,149`, `Payment.php:133,141`.
- Return cap `qty > remaining + 0.0001`: `PurchaseReturn.php:175`.
- Fix: exact comparisons on scaled decimals, no tolerances anywhere.

**P0-5 Inputs accept more decimals than the columns store**
- qty 0.00004 x rate 1,000,000 charges Rs 40.00 while qty stores as 0.0000 and no stock moves
  (`SaleController.php:133-134`). Rate 1.23456 stored as 1.2346, so reprint differs.
- Sale does not round the discount percent before use (`Sale.php:199,238`); Purchase does
  (`Purchase.php:203,225`). 7.125% applied, 7.13% stored, returns and `discountAmount()` use 7.13.
- Fix: validation `decimal:0,2` on money and percent, `decimal:0,4` on qty/rate/factor, plus column-sized max.

- Proof: 1.5 x 33.33 previews 56.49, stored 56.50. Purchase 1 x 1001.50: preview VAT 130.19, stored 130.20.
- POS quick-pay (`Pos.vue:503-511`) fills 56.49 while the backend books 56.50 cash: drawer short one paisa

**P0-9 Quotation totals computed three ways, none equal to the converted sale (3)**

### 1C. Billing records and tax

**P0-10 PAN invoices charge a hidden 13% VAT [V] (2)**
- `Sale.php:197,305` compute VAT from `vat_rate` (default 13) and `item.is_vatable` regardless of
  `invoice_type`; neither `SaleController` nor the Vue pages force 0 for `pan`. `pdf/sale.blade.php:5-6`
  hides the VAT rows for PAN, so the bill shows a 1000 line and a 1130 grand total. VAT posts to LIA20 and
  the VAT book. `SalePrintTest.php:121-139` posts exactly this without asserting VAT 0.
- Fix: server-side, `pan` forces `vat_rate = 0` and all lines non-taxable; reject disabled invoice types.

**P0-11 Voucher date never checked against its fiscal year [V] (4)**
- `JournalVoucher::post()` (`JournalVoucher.php:67-105`) resolves `FiscalYear::current()` and never
  compares `date` to `start_date`/`end_date`. Controllers only validate `required|date`.
- Stock documents bypass the fiscal-year guard entirely: `StockAdjustment.php:111-120` (unless
  `fiscal_year_id` is sent), transfers, conversions, opening-stock import.
- Scenario: auto-rollover closes the year on Shrawan 1 (`AutoStartFiscalYear.php:112`); a bill dated Asar 30
  books into the new year's ledger while the date-filtered VAT book and Day Book place it in the filed
  period. `FiscalYearReopenTest.php:201-214` does exactly this and passes.
- Fix: reject out-of-range dates in `JournalVoucher::write()`; route every dated document through the guard
  by date; matching form rule for a clean message.

**P0-12 Returns ignore the unit conversion factor on stock [V] (4)**
- `SalesReturn.php:224-230` (post) and `:398-404` (approve) record the as-entered return qty.
  `PurchaseReturn.php:173,277-283` same. Sell 2 Box (factor 12) = 24 out; return 1 Box = 1 back in.
- Fix: multiply by the original line's `unit_conversion_factor`; show the line's unit on the return form.

**P0-13 Pending and rejected return requests count as real returns [V] (3)**
- `status != 'cancelled'` in `Sale.php:146` (`outstandingAmount`, drives the allocation guard and ageing),
  `Purchase.php:142`, `VatSummaryReportController.php:77,89`, `TdsReportController.php:151`.
- A rejected Rs 1130 request permanently lowers output VAT by 130 and the invoice's outstanding by 1130.
- Fix: `status = 'posted'`.

**P0-14 Repeating a row in one request bypasses quantity and outstanding caps [V] (2)**
- Returns: `SalesReturnController.php:197` has no `distinct` rule; `SalesReturn.php:510-516` reads only
  already-stored returns. Sold 5, payload `[{line 7, qty 5}, {line 7, qty 5}]` credits 10.
- Allocations: `Receipt.php:122-147`, `Payment.php:114-139` (`PaymentController.php:56`), two rows of
  1000 against 1000 outstanding pass.
- Fix: `distinct` rule plus aggregate per target before checking.

**P0-15 Cancel reversals consume invoice and credit-note numbers [V] (3)**
- The printed invoice number is the voucher number (`SaleController.php:177-184`).
  `Sale::cancel` posts its reversal as `SaleReturn` (`Sale.php:546`), `SalesReturn::cancel` as `Sale`
  (`SalesReturn.php:603`), `PurchaseReturn` cancel as `Purchase` (`PurchaseReturn.php:334`).
  SL-5 issued, a return is cancelled (takes 6), next bill is SL-7: SL-6 never exists as a bill.
- Full and PAN invoices share one sequence but print different prefixes, so each printed series has gaps.
- Fix: dedicated reversal voucher types; a stored invoice number per series, separate from the voucher number.

**P0-16 Status transitions are unlocked: double click or two users post twice [V] (2)**
- Status checked before `DB::transaction` with no `lockForUpdate`: `Sale::cancel` (`Sale.php:516` vs
  `:534`), `SalesReturn` approve/reject/cancel (`:337/341`, `:439-446`, `:575/584`), `Receipt::cancel`,
  `Payment::cancel` (`Payment.php:193`), `CapitalSale/CapitalPurchase::cancel`, `Purchase::cancel`
  (`:516`), `PurchaseReturn` (`:326`), `JournalVoucher` cancel (`:277`), `FixedAsset` (`:257`),
  `FiscalYear::close` (`:232`), `Quotation::convertToSale` (`:88/98`, UI button has no processing guard).
- Approve and reject interleaving leaves a `rejected` return with a posted voucher that can never be cancelled.
- Fix: inside the transaction, re-read with `lockForUpdate()` (plus sale/sale-line rows for returns) and
  re-check status.

## 5. Verified correct (not to be re-audited)

- Every posting goes through `JournalVoucher::write`: at least 2 lines, one-sided lines, balance enforced inside
  the transaction (subject to P0-2 precision).
- Voucher numbering locks the sequence row inside the posting transaction; unique indexes on sequence and
  voucher; a failed post does not burn a number. (First-ever row per type is created outside the lock: can
  500 on a simultaneous first post, never duplicates.)
- No edit/delete routes and no soft deletes on posted documents; FK restrict on referenced masters.
- Sale and Purchase vouchers balance for cash/bank/partial/credit, with TDS, commission, discounts and
  non-taxable lines. VAT on post-discount taxable, exempt lines excluded, rate stored per document.
- Returns use the original price, discount share, VAT rate and TDS share, capped at sold minus returned
  (non-concurrent). Negative-qty sale lines restock correctly and cannot be returned.
- Cancel is blocked while live returns or allocations exist; JV cancel refuses module-owned vouchers.
- Trial Balance balances by construction; the open-year Balance Sheet ties.
- Year close runs depreciation, closing and opening in one transaction; only one open year; asset disposal
  balances; depreciation never below salvage.
- Legacy flagged fixes #1-#6 (2026-09-05/09) remain intact.

## 6. Remediation design

**Backend money**: brick/math `BigDecimal` (already installed; runs on 8.3 and 8.4; uses bcmath) behind:
- `App\Support\Money` (2dp, immutable): `of(string|int)` throws on float, `plus`, `minus`, `times` (exact
  multiply, one `toScale(2, HalfUp)`), `percent`, `allocate(weights)` (largest remainder, parts sum exactly),
  `isEqualTo`, `compareTo`, `jsonSerialize` to a string.
- `App\Support\Quantity` (4dp) for qty, rate, base qty and factors.
- `MoneyCast` / `QuantityCast` replacing the 95 `decimal:N` casts in 32 models; writes accept only the value
  object or a string within scale, never a silently rounded float.
- One `DocumentCalculator` used by Sale, Purchase, Quotation (create, print, convert), returns and a preview
  endpoint. Rounding points only: line gross r2(qty x rate); line discount r2; subtotals exact; header
  discount r2; taxable exact; VAT r2 once per document on taxable after discount; total exact; base qty
  r4(qty x factor); splits via `allocate()` or the remainder rule. HALF_UP (away from zero, same as MySQL
  insert rounding, symmetric for negative lines).
- Exact comparisons everywhere. Stock and report aggregates via SQL `SUM` on DECIMAL, read as strings.
- Composer: add `"brick/math": "^0.18"` directly; pin `php` to the real production version.

**Frontend money**: `resources/js/lib/money.js` with BigInt fixed point (4dp x 4dp exceeds 2^53), parse from
strings, HALF_UP away from zero, step-for-step mirror of `DocumentCalculator`, `formatMoney`/`formatQty` from
strings with en-IN grouping. Server check: Sale and Purchase submit `expected_total`; the server recomputes and
returns 422 "Totals changed, please review" on any difference. Posted documents always render stored values.
